# Story maps

Use this to organize user activities and the work needed to support them. A horizontal backbone follows the user's narrative; rows can express priority, release scope, or depth of detail. State which meaning the rows carry.

Define the user or scenario and the outcome. Keep activities distinct from supporting stories and engineering tasks. Technical work can belong on the map when its relationship to the user outcome is explicit; do not rewrite every task into an invented user benefit.

Release cuts are useful when delivery scope is the question, but an exploratory story map need not invent release commitments. Mark proposed, committed, deferred, and uncertain scope distinctly. Multiple personas or branches may need separate tracks so the shared backbone does not erase different needs.

Keep each story under its actual activity. If a story supports several activities, identify that shared scope rather than duplicating it as independent work. Show risks and dependencies when supported, without forcing a single risk card or arbitrary number of releases.

Verify activity order, story membership, user outcome, priority meaning, and release status against the source. Inspect crowded columns, release boundaries, card labels, and any filtering or expansion state used in the artifact.
