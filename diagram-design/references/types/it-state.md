# Current or target IT state

Use this for a concrete inventory of an organization's systems and their relationships, often as a current-state or target-state map. It is not automatically a modernization pitch. A current system may work well; a claimed problem or improvement needs evidence.

For current state, name the environment, observation date, sources, and coverage. Distinguish observed components and connections from reported, inferred, or unknown ones. For target state, label proposals and planned connections. If comparing states, retain stable identities and explain additions, removals, and changed responsibilities. Do not draw missing evidence as confirmed absence.

Group systems by a real property: ownership, function, location, network boundary, or lifecycle. Explain what each container means. Shared security, orchestration, or observability bars imply coverage only for the systems they actually serve. Use explicit scope labels or attachments when blanket coverage would be false.

Give edges meaningful types and directions. Queries, write paths, notifications, identity relationships, and dependencies are not interchangeable. Preserve real feedback or reverse paths. Use selected skin tokens without automatically treating one technology as a focal endpoint or one edge category as a brand-colored winner.

Start with the main operational path, place stores and external systems, then route additional connections using [primitives](../primitives.md). Derive spacing from actual labels and ports. Increase the canvas or use scoped views instead of shrinking text until the map cannot be read.

Verify component identity, environment, connection direction, boundary placement, and claimed pain or benefit against source evidence. Trace a representative operation and inspect every route that crosses a container. Compare current and proposed maps for intentional differences.
